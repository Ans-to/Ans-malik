# Blender on Colab

Two files, two purposes:

| File | Use it if |
|---|---|
| `blender_on_colab.ipynb` | you want Blender running on a Colab VM — rendering, scripting, GPU Cycles |
| `llm_blender_headless.py` | you want the `saofund/LLM-Blender-Agent` chat loop driving Blender (needs an API key) |

## Short answer

Yes. `pip install bpy` gives you Blender itself as a Python module — no display, no X server, no GUI.
A render is then just a function call in a notebook cell, and Cycles will use Colab's GPU if there is one.

What you get and what you don't:

| Works | Does not work |
|---|---|
| Cycles rendering (CPU, CUDA, OptiX) | the Blender GUI / viewport |
| Python API, `bpy.ops`, materials, geometry | the add-on panel (no UI to click) |
| headless batch renders, `.blend` files | EEVEE (needs a real GL context) |
| 4K stills, frame sequences | interactive sculpting/modeling |

**The one non-obvious setup step:** the `bpy` wheel links the X11/GL stack even when nothing will ever
draw a pixel. Without those shared objects, `import bpy` dies with
`ImportError: libXrender.so.1: cannot open shared object file`. Colab gives you root, so one
`apt-get install` fixes it — that is the second code cell in the notebook.

## Quick start

1. Open `blender_on_colab.ipynb` in Colab (`File → Upload notebook`).
2. `Runtime → Change runtime type → T4 GPU` if you want GPU renders.
3. Run all cells. The smoke test should show a chrome sphere on a dark floor in ~10–20 s.

## Limits worth knowing before you're surprised

- **`/content` is ephemeral.** The VM is recycled after ~90 min idle or 12 h hard. Push anything you want to keep to Drive *in the same cell that produces it*.
- **Session state does not survive a disconnect.** Re-running the install cells takes ~2 min.
- **Free tier is a T4 (16 GB).** Fine for 1080p at moderate samples; 4K with heavy volumetrics will OOM. Drop `resolution_percentage` before you drop samples.
- **Blender version is pinned.** `bpy==5.0.1` needs Python 3.11. If Colab ships a different Python, the notebook automatically falls back to the official 4.2 LTS tarball and drives `blender --background` instead — same scripts, one extra process.

## Can the LLM-Blender-Agent repo run here as-is?

No. Three things block the stock architecture, and only one of them is about Colab's networking:

1. **The add-on only exists inside the GUI.** You install it in *Preferences → Add-ons* and press *Start MCP Server* in the 3D viewport N-panel. A headless VM has no viewport and no preferences UI.
2. **`bpy.app.timers` never ticks without Blender's event loop.** The add-on queues every command onto the main thread through a timer; in `--background` mode there is no event loop, so the queue simply never drains. Sockets connect, commands go in, nothing comes out.
3. **`src/blender/__init__.py` imports `src.llm`, which imports every vendor SDK eagerly** (`zhipuai`, `volcengine`, `openai`, …). Importing the *Blender client* fails unless you installed all six providers, not just your one.

Port 9876 itself is not a problem — it is loopback inside the same VM. Only the Gradio port needs `share=True` to be reachable from your browser.

### Three routes

| Route | Effort | Verdict |
|---|---|---|
| **A. Xvfb + the real Blender GUI** | `apt install xvfb`, run `blender` on `DISPLAY=:1` | Unmodified repo, but software GL, ~1 GB, and the whole thing is as fragile as a hidden GUI gets. Use only if you need the viewport. |
| **B. In-process bridge** (`llm_blender_headless.py`) | drop in one file, call `install()` | Recommended. Keeps the agent loop, providers, and Gradio UI; replaces only the socket with a direct dispatcher that speaks the same JSON envelopes as the add-on. |
| **C. Skip the agent** | none | If all you want is Blender, the notebook alone is enough. |

### Route B, concretely

```python
# after the bpy cell of blender_on_colab.ipynb
!git clone https://github.com/saofund/LLM-Blender-Agent.git /content/llmba
%cd /content/llmba
!pip -q install "anthropic>=0.40" tenacity gradio        # only the provider you actually use

# upload llm_blender_headless.py to /content first (Files pane -> Upload)
import sys; sys.path.insert(0, "/content")
import llm_blender_headless as bridge
client = bridge.install()          # also rebinds src.blender.BlenderClient for the Gradio app
client.get_scene_info()["result"]  # {'name': 'Scene', 'object_count': 0, ...}
```

Then put a key in `config.json` (`llm.claude.api_key`, or whichever provider you installed) and start
`app.py`. The bridge implements the same nine command types as `addon.py`, with the same parameter
names and result keys, so the agent's tool list and the UI's render pane work untouched.

Two handlers are deliberately **disabled**:

- **`execute_code`** — arbitrary `bpy`/Python generated by a language model. Upstream leaves it out of the tool list for the same reason; the instruction surface should not reach arbitrary code execution.
- **`generate_3d_model`** — needs a second machine serving Hunyuan3D-2 with 46 GB (mini) to 115 GB of weights.

Also be aware, all from reading the source rather than running it:

- The README advertises **Poly Haven** and **Hyper3D Rodin**; `addon.py` contains neither. Those docs are inherited from the upstream BlenderMCP project.
- `doc/project_structure.md` documents a `cli.py` that does not exist.
- `LICENSE` is Apache-2.0, while the README footer says MIT.
- Last commit was 2025-03-27; two model IDs in `config.json` (`claude-3-7-sonnet-20250219`, `kimi-latest-32k`) may already be retired.

## What is verified, and what isn't

Being precise about this matters, because none of it can be executed here — this sandbox has no root, so
the X11/GL stack can't be installed and `import bpy` fails locally.

**Verified by running:**

- `bpy 5.0.1` installs from PyPI on Python 3.11 (the wheel exists and pins `cp311`).
- Every Python cell in the notebook compiles; the scene template compiles after token substitution.
- The bridge's nine handlers run end-to-end against a mock `bpy`, driven through the repo's **real**
  `BlenderClient` wrapper methods — `create_object`, `set_material`, `modify_object`, `get_object_info`,
  `delete_object`, `render_scene`, and `save_render_image`'s base64 round-trip. Envelopes match
  `addon.py`'s `{"status": ..., "result": ...}` shape, including the error paths.
- The `download.blender.org` 4.2 LTS filenames used by the fallback (4.2.19 is current).

**Not verified — needs your Colab:**

- The real `bpy` import against real Blender (the apt list is the standard one for headless Blender; the failure mode, if any, is a missing `lib*` name and it will be named in the error).
- GPU timings. The notebook measures and prints them rather than asserting a number.
- The agent loop talking to a live model. The bridge has never seen an API key.

If the smoke test renders, everything below it works. If it doesn't, the failing cell names the missing
library — send it back and the apt list gets one more entry.
